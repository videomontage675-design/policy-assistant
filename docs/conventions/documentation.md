# إرشادات التوثيق

- الغرض: وثائق يستطيع منها شخص جديد أن يفهم المشروع ويكمل العمل دون أن يسأل.
- الجمهور: كل من يكتب وثيقة في المشروع.
- آخر تحديث: قبل المرحلة 1.

## المبادئ
1. التوثيق ككود (Docs-as-code): كل الوثائق ملفات Markdown داخل المستودع، وتُحدَّث في نفس الـ commit مع التغيير الذي تصفه.
2. مصدر واحد للحقيقة: لا تنسخ معلومة موجودة في ملف آخر؛ اربط إليها برابط نسبي.
3. القابلية للتتبع: كل وثيقة تصميم أو قرار تذكر معرّفات المتطلبات التي تخدمها.
4. اكتب للقارئ: ابدأ بالخلاصة ثم التفاصيل. جمل قصيرة. مثال ملموس واحد أفضل من فقرة شرح.
5. افصل الحقيقة عن الافتراض: كل افتراض يُعلَّم صراحة بعبارة «افتراض:».

## رأس كل وثيقة
كل ملف في `docs/` يبدأ بثلاثة أسطر:
- الغرض: سطر واحد.
- الجمهور: مطوّر / مالك المتجر / الاثنان.
- آخر تحديث: المرحلة أو التاريخ.

## بنية مجلد docs
```
docs/
├── requirements.md     المتطلبات والقيود (مصدر واحد)
├── traceability.md     مصفوفة: متطلب ← مكوّن ← ملف ← حالة
├── architecture/       ADR-NNN-short-title.md
├── phases/             phase-N-plan.md و phase-N-report.md
├── conventions/        إرشادات العمل والتوثيق والتطوير
└── templates/          قوالب ADR وتقرير المرحلة
```

## سجلات القرار (ADR)
- متى تكتب ADR: اختيار تقنية أو مكتبة أو خدمة خارجية، تغيير بنية البيانات، أي قرار يصعب التراجع عنه.
- ملف لكل قرار: `docs/architecture/ADR-NNN-short-title.md`، بترقيم متسلسل من ثلاث خانات.
- استخدم القالب `docs/templates/adr.md`.
- الحالات: مقترح / معتمد / مستبدَل بـ ADR-NNN.
- ADR المعتمد لا يُعدَّل محتواه. لتغيير القرار: أنشئ ADR جديداً، وغيّر حالة القديم إلى «مستبدَل بـ ADR-NNN».

## مصفوفة التتبع (traceability.md)
جدول واحد بالأعمدة: المعرّف | المتطلب (مختصر) | المكوّن | الملفات | الاختبار | الحالة (مخطط / منفّذ / مُختبر).
كل متطلب في `docs/requirements.md` له صف، حتى لو كانت حالته «مخطط».

## الرسوم التوضيحية
- استخدم Mermaid داخل Markdown (يعرضه GitHub مباشرة). لا تستخدم صوراً لرسوم يمكن كتابتها نصاً.
- كل رسم يسبقه سطر يشرح ما يوضحه.

## CHANGELOG.md
بصيغة Keep a Changelog: عنوان لكل مرحلة مع التاريخ، وتحته أقسام Added / Changed / Fixed / Removed حسب الحاجة.
